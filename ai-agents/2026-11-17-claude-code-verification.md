# Claude Code 团队怎么让代理“自己验收”：写一个 verify 技能、修三轮还不过就叫人、改动不能改自己的检查

**一句话结论**：Claude Code 团队约 90% 的代码由 Claude 写、由 Claude 审。11 月 16 日，Addy Osmani 在官方博客写了他们怎么让代理拿证据证明“改好了”。核心观点：真正跑一遍比单测管用，验收步骤要写成代理能自己调用的技能，判定规则不能让被检查的改动去改。这些做法不依赖 Claude，放到 Codex、OpenCode 上也能照搬。

## 要点

- **最值得投入的三种测试**：
  - **端到端测试**：模拟真实用户流程（比如加购物车、下单、到确认页），整个功能要么能用要么不能用，最难被糊弄。单测能全过而功能照样坏。
  - **性质测试（property test）**：先写一条“不可能被打破”的规则，再用 fast-check（JS/TS）、Hypothesis（Python）、proptest（Rust）生成成千上万个输入去证伪。常见规则：编码再解码得到原值；余额永远不为负；同一操作做两次和做一次效果一样；优化后的代码和朴素实现结果一致。好处是边界输入不带写代码那个代理的偏见。
  - **差分测试**：迁移、重写时，新旧系统喂同样的输入（随机生成或抽样生产流量），结果不一样就是 bug。要把空白这类无关差异先抹平，并维护一份“允许不同”的清单。
- **写一个叫 verify 的技能**：把“怎么启动应用、怎么跑一遍”写成技能放进仓库的 `.claude/skills/`，尽量靠近相关代码，可以有多个。Claude 提交前会用它。这个技能就是你的冒烟测试，值得让 Claude 反复打磨到稳定可靠。网页改动让它用浏览器扩展去点，移动端用模拟器，后端就在本地把服务跑起来。
- **修三轮还不过就叫人**：Claude 跑检查、自己修；同一个检查失败三轮后停手，找人来看。
- **按改动触发检查清单**：团队有一份 39 条的可靠性清单，每条写明“从改动里能看出来的触发条件”、怎么查、以及当初是哪次事故催生的。Claude 读改动，只查触发条件对得上的那几条（通常 3 到 10 条），没人需要背历史事故。
- **改动不能改自己的检查**：审查规则文件 REVIEW.md 从主分支读，不从这次的 PR 里读；规则放在改动碰不到的分支上。审查结果只对应某个提交，审查期间又推了新代码，结果就作废。先跑便宜的检查：开 PR 前 Claude 先跑测试、构建和 lint，可以用 hook 在 Claude 做完时自动跑测试来强制。
- **新门槛先“观察模式”**：他们给每个提交标上验证方式（包括“none”，方便查哪些没验证）。新加的提交门槛分关闭、观察、强制三档：观察模式只记录本该拦下的，确认没有误拦再强制；同一会话被拦两次后放行第三次，免得 Claude 卡死。

## 适合谁

- 同时开多个代理并行干活、没精力逐个检查结果的人。文章的说法是：没有验证闭环，一次只能盯一两个；有了，可以并行几十上百个。
- 让代理做重构、迁移的人，性质测试和差分测试最对路。
- 维护代理服务（比如 Telegram 桥）的人：把“改完必须跑的冒烟测试”写成技能或 hook，比每次在提示词里提醒靠谱。

## 注意事项

- **测试不稳会把代理教坏**：时过时不过的测试，会让代理学会“再跑一次”而不是去修代码；太慢的测试会让代理少跑。重的测试放在提交前跑。
- **别让代理改判定它的东西**：测试、审查规则、门槛脚本要放在这次改动改不到的地方，否则检查形同虚设。
- 文中“用独立评分者对照评分标准检查，任务成功率最多提高 10 个百分点”是 Anthropic 在结构化文件生成任务上的内部测试结果，换个场景不一定成立。
- 文中那个“会话里没跑过 `/code-review` 或 `/verify` 就拦下提交”的门槛，是 Claude Code 团队在自己仓库里搭的，想照做得自己实现。
